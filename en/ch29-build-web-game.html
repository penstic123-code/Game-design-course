Make a Small Web Game

No need to learn programming first. Read a 100-line little game, then turn its knobs.

⏱ About 60 minutes (hands-on included)

Learning goals

  • Say what HTML, CSS and JavaScript each handle, and how the “input → update → draw” game loop makes the picture move.
  • Explain why the game loop looks the way it does, and why web games went from Flash to Canvas.
  • Drag a parameter panel and see for yourself the relationship “numbers → play → feel,” and know the limits of this kind of tuning.
1

What it isThree roles: who handles the skeleton, who the looks, who the rules

Many people want to make a game, see a screenful of code, and close the page. A playable little game is only about 100 lines of code. You needn’t finish learning programming first; it is enough to tell what each of three roles does. Think of cooking:

A game’s “design” almost all lands in JavaScript: goals, rules, feedback and numbers are, in code, just a few variables and a few conditions. Three examples show what each role’s job really is:

In the game: making the basket wider. This is a number at the rules level (P.width on this page, written in the JS). Changing the page background color is CSS’s business; putting a game area on the page is HTML’s <canvas>.
Daily life: cooking a meal. The ingredient list is HTML (what’s there), plating and tableware are CSS (what it looks like), and the recipe’s steps and heat are JavaScript (how to cook it and when).
Counterexample: a scoring game made with only HTML and CSS. CSS can animate, but “judging whether the apple landed in the basket, adding points, taking away a life” is rules and needs JavaScript to compute. Only looks, no referee.

What it isHow the browser turns them into a picture

Once the browser has these three, it runs a pipeline to produce the picture. Games use the canvas, which takes a shortcut:

The order of steps follows MDN’s “critical rendering path” page (DOM, CSSOM, render tree, layout, paint). The dashed Canvas line is a sketch: it hands the finished bitmap to the page to display.

Games like the canvas because an ordinary web page works by “typesetting”: with many elements, every change means recalculating positions. A canvas works by “painting”: how many balls to draw and where is decided by the program each frame, which suits games that must redraw dozens of times a second.

What it isThe game loop: input → update → draw

A web page usually changes only after the player clicks; a game goes round and round, and even if you press nothing, the apple keeps falling. Seeing the two side by side:

A game program turns round and round in this way, and in structure it is a game loop. The browser calls our function about 60 times a second (about 60 frames/second), and each pass does three things, which is the technical version of the core loop:

Concept card

Game Loop

Game loop

Robert Nystrom · Game Programming Patterns (2014) organized it as a design pattern (separating game time from player input and processor speed); Spacewar! (1962) was an early form of the real-time loop

On each pass the program reads input, updates state and draws the picture, without waiting for a key press, pass after pass; that is how the picture moves by itself.

ExampleIn an apple-catching game the player touches no key, yet every pass an apple falls a little further, and a missed one costs a life.

In the game: catching apples. Even if you don’t touch the keyboard, the apple falls a little on every pass, and a miss costs a life. This is “continuous updating.”
Daily life: a flip book. Flip a few dozen pages a second, each page differing from the last by a tiny movement, and the eye sees “motion.” The game loop does the same thing: draw one page every pass.
Counterexample: writing your own infinite loop. Write while (true) {…} in a function, updating and drawing forever yourself, and the browser’s main thread is fully occupied: the page freezes and buttons can’t be clicked. Have the browser “call your program once per frame” (with requestAnimationFrame) instead of hogging the loop yourself.

Invention storyHow did the game loop become the standard structure?

Try it yourself first. Suppose you wrote a little ball game: the ball moves 20 cells per second and reaches the finish after 100 cells. You tuned the speed on your own computer (60 frames/second). Now you put it on two other computers: one very fast, one very slow. Drag the slider and compare the two ways of writing it.

Slow computer (30 frames/second)

Try it: race once without dt, then race once with dt, and compare “how many times slower” in the two races.

Why does the game loop look like this?

Early programs were “batch”: run once, spit out a result, end. Later came interactive programs, the first of which were games, such as the text adventure Colossal Cave Adventure, which waits for a command from the player, responds, then waits again. Action games can’t wait: even if the player presses nothing, bullets must fly and enemies must move. (From the game-loop chapter of Robert Nystrom’s Game Programming Patterns.)

In 1962 Steve Russell and others at MIT made Spacewar! on the PDP-1 minicomputer, which influenced many later arcade games, and the first form of the loop is in it. But games then were often tied to the speed of one particular machine: how far to move each pass was tuned to that machine. Nystrom mentions that on a faster computer such games became too fast, and the “Turbo button” on personal computers of the time had to do with this.

The later approach was to separate “game time” from “processor speed and player input”: the game loop processes player input but doesn’t wait for it, and lets the game run at a consistent speed on different hardware (Nystrom).

There are two common ways to do the separating. ① Variable time step: each pass advances by “the real time since the last pass, dt”; simple, good for small games, and what this page uses. ② Fixed time step: each update advances a fixed small slice of time; more stable, and more commonly used in games with complicated physics.

Moving the game loop onto the web took another winding road. Web pages began as static documents, and for a long time animated little games relied on plug-ins. Flash’s predecessor was released in 1996 and later taken over by Macromedia and then Adobe. Flash let many creators make animated little games without deep programming and distribute them in the browser.

Meanwhile in 2004 Apple added <canvas> to its own WebKit, Gecko and Opera followed, and it was later folded into HTML5 by the WHATWG. In April 2010 Steve Jobs published the open letter “Thoughts on Flash” explaining why the iPhone does not support Flash, citing reasons including that Flash is a closed system, and battery life and touch problems. Adobe held that it was mainly a business consideration.

In July 2017 Adobe announced it would end support for Flash on December 31, 2020. Now the natively supported <canvas> + JavaScript is the foundation of web games.

Working with this is requestAnimationFrame, which has the browser call the program’s function “before the next repaint,” usually matching the display’s refresh rate (60, 75, 120, 144 Hz and so on). The callback receives a timestamp that must be used to compute progress, or the animation will run faster on high-refresh-rate screens, and this is where the trap in the race above lies.

Why it holdsWhy multiply by dt? Why is tuning parameters a shortcut?

① Why updates multiply by dt

A device with a high frame rate has more passes a second, but each pass should only take a small step. position += speed × dt makes “how far per second” independent of frame rate, which separates game time from processor speed.

It is like walking: say “1.4 meters per second,” not “70 centimeters per step,” and people with different strides can still compare speeds. Write the apple’s fall as it.y += P.speed * dt, and on a 60 Hz screen and a 144 Hz screen the distance fallen per second is the same.

Conversely, adding a fixed 3 pixels per pass gives 180 pixels a second on a 60 Hz screen and 432 pixels a second on a 144 Hz screen. This is why “the fast computer arrives first” in the race above.

Concept card

Delta Time

Delta time

Robert Nystrom · Game Programming Patterns (2014), the “Game Loop” chapter, explains advancing the game by real elapsed time

dt is the real time since the last pass. Moving by “speed times dt” on each pass makes the distance an object covers per second independent of the frame rate.

ExampleAn apple falls 200 pixels a second: on a 60-frame screen it moves about 3.3 pixels per pass, on a 144-frame screen about 1.4, and after one second it is at the same place.

Boundary: for readability this page uses a “variable step” and limits dt to 0.05 seconds (so returning from another tab doesn’t “teleport” things). Games with more complicated physics more commonly use a fixed step in the industry.

Source of the principle:
Robert Nystrom · 2014 · the “Game Loop” chapter of Game Programming Patterns, which separates game time from processor speed.
MDN · the requestAnimationFrame documentation.

② Turning a knob is walking “mechanics → dynamics → aesthetics” by hand

The MDA framework says: the designer sets out mechanics, and what the player experiences is dynamics and aesthetics. The parameter panel puts this chain before your eyes: what you turn is the mechanics (fall speed, basket width, bomb probability), what you see is the dynamics (whether you can catch, whether to take a risk), what you feel is the aesthetics (relaxed, tense, flustered).

These numbers are like the knobs on a radio: turn one and the feel changes. Pull the bomb probability from 15% to 40% and the hesitation over “should I reach for it” grows at once, the feeling going from relaxed to tense. Turn only one at a time, to know which one did the work, like adjusting the grind of coffee, changing one variable at a time.

Change speed, basket, bombs and lives all at once, and all you get is “it’s harder now,” without knowing which knob deserves the credit or which way to tune next.

Boundary: tuning parameters can polish a core loop that already works, but can’t rescue a loop that isn’t interesting in itself; and how fun it is depends not only on the numbers but also on the structure of the rules.

Source of the principle: Robin Hunicke, Marc LeBlanc and Robert Zubek · 2004 · proposed the MDA framework: mechanics produce dynamics, and dynamics produce aesthetics.

③ Worldview: every frame is still, and “motion” is filled in by the brain

The game loop draws a still picture on each pass, yet the eyes feel the ball moving. In 1912 Max Wertheimer ran a series of experiments: two still points of light flash briefly one after the other, and with a suitable interval people see a single point moving; this is apparent motion (the phi phenomenon). This paper is often seen as the starting point of Gestalt psychology.

Remember the flip book? The brain fills in motion between two still pictures. A game’s “smoothness” relies on still pictures dense enough, with the brain connecting them.

Phi is often confused with another phenomenon, “beta movement,” and the actual visual mechanism is more complicated than described here.

④ Worldview: all models are wrong, but some are useful

The “difficulty index” on the page is pieced together with a crude formula, and real difficulty depends on the player’s hand speed, habits and mood, which a formula can’t compute. The statistician George Box said: “All models are wrong, but some are useful.” What’s useful is to take the model’s predictions to playtests, be corrected by reality, and then revise the model.

How to use itWhat to learn next

  

    
1. JavaScript basics
Variables, conditions, loops, functions, arrays and objects, events. Once you can read the code above, a systematic study goes much more smoothly. MDN Web Docs has free tutorials.

    
2. Pick an engine
Phaser: a JS framework made for 2D web games, continuing this path. Godot: free and open source, with a scripting language, GDScript, close to Python, good for beginners. Unity: uses C#, with plenty of material and jobs. Pick one first; don’t learn three at once.

    
3. Join a game jam
Make a small game around a theme in 48 hours or a few days, such as Global Game Jam or Ludum Dare. The short time forces you to cut the scope to the minimum.

    
4. Make it small but complete
Take every project to “a game that can be played through” and send it to others to playtest. Finishing 5 small games teaches far more than abandoning 1 big game halfway.

  


  

    
Common misconceptions

    
    
      
  • “Start by making the full game”: first make a small thing you can play through once; the smaller the scope, the easier to finish.
    • 
      
  • “You must finish learning programming before you start”: reading a small game and then changing it is a more efficient way in.
    • 
      
  • “A prototype must look good”: the apples and basket here are plain, but enough to verify the play.
    • 
      
  • “The harder the difficulty the more challenging”: extreme parameters are not the same as fun; use the hints in the panel and your own playtests to find “just right.”
    • 
      
  • “Tuning parameters can rescue any game”: when the core loop doesn’t hold, adjusting numbers only spins in place.
    • 
      
  • “Moving a fixed amount per pass is fine, no need for dt”: then the game speeds up or slows down with the device’s frame rate (the race above has already shown it).
    • 
    

  


  

    
Something to think about

    
What does your favorite set of parameters make the player “feel” (tension? ease?), and which knob deserves most of the credit? If you were allowed to change only one knob, which would you change, and why?

    
    
A contested question: was the death of Flash technological progress, or the price of a closed ecosystem? The Flash era left behind a large number of creative little games, and some, unable to run after Flash was turned off, face being lost. Open standards and the preservation of creators’ work often have to be considered together.

  


  

    
Key points

    
    
      
  • HTML builds the structure, CSS handles the looks, JavaScript writes the rules; game design is mainly embodied in the state and conditions in the JS.
    • 
      
  • The game loop: input → update → draw, about 60 passes a second, not waiting for input; multiply by dt in updates so game time is separate from machine speed.
    • 
      
  • Web games went from the plug-in era (Flash) to native Canvas + JavaScript.
    • 
      
  • Every frame is a still picture and the “motion” is filled in by the brain; formulas like the difficulty index are crude models and need correcting by playtests.
    • 
      
  • Putting adjustable numbers together in one parameter object makes it easy to iterate after playtests. Make something playable first, then get better step by step.
    • 
    

  

  
Turning rules into numbers, then turning the knobs yourself and watching the consequences, is the fastest way to understand “mechanics → dynamics → aesthetics.” But it polishes a loop that already works and cannot replace a good idea.
